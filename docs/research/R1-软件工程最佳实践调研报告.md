## 1. 分层架构与模块边界

### 1.1 最佳实践要点

- **经典三层职责**：接口层（路由）只做参数解析、鉴权、调用服务、组装响应；服务层承载全部业务规则与事务边界；数据访问层集中所有 SQL/ORM 操作。路由层出现 SQL 或复杂分支是典型的"贫血控制器缺失"反模式。
- **依赖方向单向向下**：`api → services → repos → models`。上层知道下层，下层不知道上层；服务之间避免横向循环依赖，公共能力下沉到 core。
- **契约与实体分离**：对外的 Pydantic schema（请求/响应模型）与数据库表结构分开定义，避免 DB 字段变更直接穿透到 API 契约。
- **配置与代码分离**：任何环境差异（路径、端口、密钥、开关）不得写死在代码里，统一由配置模块注入（详见第 2 章）。
- **按业务域切模块**：小系统也应按"患者问诊 / 医生后台 / 认证 / 第三方语音 AI"划分边界，而不是按技术类型把所有 service 堆一个目录。

### 1.2 对本项目的落地建议

推荐目录结构（FastAPI 单体，单机规模不做微服务拆分）：

```
zhongyi/
├─ app/
│  ├─ main.py            # FastAPI 装配：中间件、全局异常处理器、路由注册
│  ├─ core/
│  │  ├─ config.py       # Settings（pydantic-settings，唯一配置入口）
│  │  ├─ logging.py      # 结构化日志、trace-id、脱敏过滤器
│  │  ├─ security.py     # 密码哈希、会话管理、登录失败锁定
│  │  └─ errors.py       # 业务异常类、错误码常量、全局异常处理器
│  ├─ api/
│  │  ├─ patient.py      # 患者端路由（无登录、弱凭证+限流）
│  │  ├─ doctor.py       # 医生后台路由（强鉴权依赖）
│  │  └─ deps.py         # 依赖注入：当前医生会话、当前问诊会话、DB 连接
│  ├─ schemas/           # Pydantic 请求/响应模型（对外契约）
│  ├─ services/          # 业务逻辑：consult_service、summary_service、auth_service
│  ├─ repos/             # 数据访问：全部 SQL 集中于此
│  └─ models/            # SQLite 表结构定义
├─ migrations/           # 版本化迁移脚本 001_init.sql …（见第 9 章）
├─ web/dist/             # 前端构建产物（Nginx 托管）
├─ scripts/              # backup.sh / restore.sh / deploy.sh / cleanup.sh
├─ deploy/               # zhongyi.service、nginx.conf、env.example
├─ tests/{unit,integration}/
└─ requirements.lock
```

各层硬性分工：

| 层 | 允许做 | 禁止做 |
|---|---|---|
| api 路由 | Pydantic 校验、鉴权依赖、调 service、包装响应 | 写 SQL、写业务判断、直接操作 sqlite3 连接 |
| services | 业务规则、事务边界、调用第三方客户端、记业务日志 | 直接接触 HTTP Request/Response 细节 |
| repos | CRUD 与查询 SQL | 业务判断、感知 HTTP |
| core | 配置、日志、安全、错误码等横切能力 | 包含业务语义 |

本项目特有边界：患者端与医生端路由物理分文件，鉴权策略完全不同（患者端=一次性问诊凭证+限流，医生端=服务端 Session 强鉴权），不允许共用鉴权依赖；ASR/LLM 第三方调用封装为独立 client 类并定义 Protocol 接口，便于测试时替换假实现（见第 8 章）。SQLite 并发写有限，事务边界收敛在 service 层、单事务内完成"摘要入库"，避免跨请求长事务。

## 2. 配置管理（12-Factor）

### 2.1 最佳实践要点

- **12-Factor III（配置）**：配置与代码严格分离，一切随环境变化的内容存于环境变量；同一份代码可部署到开发/测试/生产而不改动。[来源：12factor.net]
- **密钥不入库**：`.env` 加入 `.gitignore`，仓库只提交 `.env.example`（键名齐全、值为占位符）；SECRET 类值用 `openssl rand -hex 32` 生成。
- **单一配置入口**：用 pydantic-settings 的 `BaseSettings` 定义强类型 Settings 单例，支持环境变量覆盖 + `.env` 文件兜底，类型错误在启动时报出而非运行中爆炸。
- **fail-fast**：应用启动时校验必填项（如 SECRET_KEY、第三方 API Key），缺失立即拒绝启动并列出缺失键名。
- **环境切换**：以 `APP_ENV=dev|test|prod` 一个变量驱动行为差异（日志级别、是否允许真实外呼、CORS 等），其余配置各自赋值，不搞多套配置文件复制粘贴。

### 2.2 对本项目的落地建议

必须纳入配置的清单：

| 键 | 说明 |
|---|---|
| APP_ENV | dev / test / prod |
| SECRET_KEY | 会话签名/令牌哈希盐，`openssl rand -hex 32` |
| DB_PATH / DATA_DIR / LOG_DIR | 数据库文件、数据目录、日志目录（相对 BASE_DIR 或绝对均可重定位） |
| ASR_API_KEY / LLM_API_KEY / 相关 endpoint | 第三方语音识别与摘要生成凭证 |
| SESSION_TIMEOUT_MINUTES=30、LOGIN_LOCK_*=5/15 | 安全参数显式化 |
| UPLOAD_MAX_MB、AUDIO_MAX_SECONDS | 音频上传上限 |

落地要点：

1. 生产环境由 systemd 的 `EnvironmentFile=/opt/zhongyi/env` 注入（root 属主、权限 600，普通用户不可读）；开发用项目根 `.env`。
2. `APP_ENV=test` 时 Settings 强制要求所有第三方客户端指向 Fake 实现，从机制上杜绝测试打真实外呼。
3. 代码评审红线：grep 不到任何硬编码密钥/IP/绝对路径；新增配置必须先加进 `.env.example` 与本文档清单。
4. 不引入配置中心/Apollo 之类组件——单机规模下环境变量 + env 文件即可满足，符合"最轻方案保质量"。

## 3. 日志体系

### 3.1 最佳实践要点

- **结构化优先**：生产日志输出 JSON 行格式（stdlib logging + python-json-logger 即可，无需重型方案），字段固定：`time, level, logger, event, trace_id, module, msg, extra`。文本日志在排障聚合、字段过滤上成本高得多。
- **四级分级使用约定**：
  - `DEBUG`：开发细节（默认关闭）；
  - `INFO`：关键业务事件（问诊会话创建/提交、登录成功、备份完成）；
  - `WARNING`：可预期异常但需关注（限流触发、登录失败、第三方超时重试、磁盘水位）；
  - `ERROR`：未捕获异常、外部依赖持续失败（附堆栈）。
- **请求级 trace-id 贯穿**：中间件为每请求生成 `uuid4`（或透传上游 `X-Request-ID`），存入 contextvar，所有日志自动携带；同时写入响应头 `X-Request-ID` 与错误响应体，实现"用户报错 → 一条 trace_id → 定位全链路日志"。
- **敏感信息脱敏是医疗类系统的硬约束**：凭据、身份证号、手机号等常规脱敏之外，本项目还有更严格的红线（见下）。

### 3.2 对本项目的落地建议

**日志内容红线（最高优先级）：**

1. 任何级别日志**不得包含**：音频内容或其编码片段、逐字转写文本、病情摘要九栏目正文、患者主诉原文。（与 PRD 最小化留存边界一致：录音与转写本就不落盘，日志同样不得间接留存。）
2. 日志只允许记录元数据：record_id、轮次数、音频字节数、时长、耗时、状态码、错误类别。
3. **就诊号脱敏规则**：就诊号单独无识别性，但"就诊号+日期+科室"组合可定位到人，故：
   - 日志关联排查统一使用内部代理键 record_id（自增/UUID），不以就诊号为主关联键；
   - 如需打印就诊号，必须经 `mask_visit_no()`：长度 ≤2 位整体星号化（`35`→`**`）；3–5 位保留首末各 1 位（`123`→`1*3`）；>5 位保留前 2 后 2；
   - 同一行日志禁止出现完整"就诊号原文+完整日期"组合。
4. 第三方 API Key、SECRET_KEY、Cookie 值不落日志；异常堆栈中的请求体要过滤后再记录。

**审计日志单独成文件**（audit.log，JSON 行，保留 ≥180 天）：登录成功/失败、登出、医生查看记录列表/详情、数据删除、管理员解锁账号。字段：`who(doctor_id), action, target(record_id), ip, ua, result, time`。这是"谁看过病情摘要"的唯一追责依据，与应用日志分开管理。

**实现与运维：**

- `RotatingFileHandler`：app.log 单文件 50MB × 10 个滚动；audit.log 独立 Handler 独立滚动；不依赖 journald 格式，保证日志目录可整体打包带走。
- 关闭 uvicorn 默认 access log，改由中间件输出带 trace_id 的请求日志（method, path, status, duration_ms, bytes），query string 一律不记（防凭证经 URL 泄漏）。
- 提供脱敏工具函数 `mask_visit_no()` 并列为必测点（见第 8 章）。

## 4. 异常处理与错误码规范

### 4.1 最佳实践要点

- **全局异常处理器兜底**：FastAPI 注册 `@app.exception_handler(Exception)`，未捕获异常统一转为 500 + trace_id 返回，完整堆栈只进 ERROR 日志，绝不下发给客户端（防内部信息泄漏）。
- **业务异常类驱动**：定义 `BizError(code, message, http_status)`，service 层抛出、全局 handler 统一翻译；路由层不写 try/except 收尾逻辑。
- **对外错误响应统一格式**，且 HTTP 状态码本身也要语义正确（监控、网关才能正确计数）。
- **错误码登记表**：错误码是跨前后端的契约，必须有唯一权威文档，新增必须登记，防止码值冲突和前端漏处理。

### 4.2 对本项目的落地建议

**统一响应格式**（成功与失败同构）：

```json
{"code": 0, "message": "ok", "data": { }, "traceId": "…"}
{"code": 3001, "message": "登录已过期，请重新登录", "data": null, "traceId": "…"}
```

**错误码分段设计**（千位段划分，登记于 `docs/error-codes.md`）：

| 段 | 含义 | 示例 |
|---|---|---|
| 0 | 成功 | — |
| 1000–1999 | 系统/内部错误 | 1000 内部错误；1001 数据库不可用 |
| 2000–2999 | 参数与校验 | 2001 参数缺失/格式非法；2002 就诊号非法；2010 音频过大；2011 音频格式不支持；2012 时长超限 |
| 3000–3999 | 认证与会话 | 3001 未登录/会话过期；3002 用户名或密码错误；3003 账号已锁定；3010 问诊凭证无效/已过期 |
| 4000–4999 | 业务规则 | 4001 问诊会话不存在或已结束；4002 轮次超限；4003 已提交不可重复提交；4004 记录不存在 |
| 4300–4399 | 频控 | 4301 请求过于频繁 |
| 5000–5999 | 第三方依赖 | 5001 ASR 超时；5002 ASR 失败；5010 摘要生成失败 |

**HTTP 状态映射**：2000 段→400/422；3001→401；403→权限类；4301→429；1000 段→500；5000 段→502/504。Pydantic 自带的 422 响应需自定义 handler 改写成上述统一格式。

**文案原则**：面向老年患者的提示语由前端根据 code 映射为大字友好文案；后端 message 保持中性技术描述；登录失败提示不区分"账号不存在/密码错误"（防枚举，见第 5 章）。

## 5. 安全基线

### 5.1 会话认证：服务端 Session vs JWT

| 维度 | 服务端 Session | JWT |
|---|---|---|
| 登出/吊销 | 删除服务端记录即即时生效 | 困难：需黑名单，等于重新引入服务端状态 |
| 过期模型 | 滑动过期天然支持（刷新最后活跃时间） | 需 refresh token 双 token 机制，复杂度高 |
| 服务端存储 | 需要（内存/SQLite/Redis） | 无需（自包含签名） |
| 多实例扩展 | 需共享存储 | 天然无状态 |
| 凭证泄露后果 | 可立即失效该会话 | 有效期内无法收回 |
| FastAPI 实现成本 | 低 | 中 |

**结论：本项目医生后台采用服务端 Session，不用 JWT。** 理由：单机部署无多实例共享诉求；"30 分钟无操作登出"用滑动过期一行判断即可；管理员需要"强制某医生下线/全端下线"能力时 Session 是删一条记录的事，JWT 做不到。OWASP 会话管理清单同样强调空闲超时与服务端失效控制的重要性。

落地：opaque 随机令牌 `secrets.token_urlsafe(32)` 存 SQLite 会话表（doctor_id、创建时间、最后活跃时间），Cookie 仅携带令牌，属性强制 `HttpOnly + Secure + SameSite=Lax + Path=/`；每次请求刷新 last_active，超过 30 分钟未活跃则删除会话并返回 3001；登出删除记录。患者端无账号体系：开始问诊时签发一次性问诊凭证（绑定就诊号与有效期），同样服务端存储校验，不用自包含 JWT。

### 5.2 密码存储

依据 OWASP 密码存储清单：

| 方案 | 结论 | 参数 |
|---|---|---|
| Argon2id | **首选** | OWASP 最低线 m=19 MiB(19456)、t=2、p=1；Python 库 argon2-cffi |
| bcrypt | 次选可用 | cost 下限 10，本项目建议 ≥12；注意 72 字节输入上限 |
| PBKDF2-HMAC-SHA256 | 仅 FIPS-140 合规场景使用 | ≥600,000 次迭代 |
| MD5/SHA 系裸哈希、可逆加密 | **禁止** | GPU 可秒破 |

### 5.3 登录失败锁定

- 连续失败 **5 次 → 锁定 15 分钟**（到期自动解锁，管理员可提前手工解锁）。OWASP 明确：失败计数器应挂在**账号维度**而非 IP，否则攻击者换 IP 即绕过；同时登录接口叠加 IP 维度限流（10 次/分钟/IP）抵御跨账号口令喷洒。
- 失败提示语统一"用户名或密码错误"，不暴露账号存在性；每次失败写 WARNING 应用日志 + audit.log（账号掩码、IP、UA）。
- 医生账号仅管理员预建，无自助注册/找回入口，攻击面天然收窄。

### 5.4 安全响应头（Nginx 统一加，`always` 保证错误响应也带）

| 头 | 值 | 备注 |
|---|---|---|
| Strict-Transport-Security | max-age=31536000; includeSubDomains | 全站 HTTPS 后启用 |
| X-Content-Type-Options | nosniff | 必加 |
| X-Frame-Options | SAMEORIGIN | 后台防点击劫持 |
| Content-Security-Policy | default-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self' | 若用微信 JS-SDK 需追加其脚本域名 |
| Referrer-Policy | strict-origin-while-cross-origin → 取 strict-origin-when-cross-origin | 默认收紧 |
| Permissions-Policy | microphone=(self) | **严禁配置为 microphone=()——患者页核心功能就是麦克风** |
| Cache-Control（含摘要的 API 响应） | no-store | 防 H5 缓存残留病情摘要 |

### 5.5 限流防滥用（重点：患者端无登录提交接口）

双层限流：Nginx `limit_req_zone` 按 IP 全局兜底 + 应用层 slowapi 按接口精细控制。

| 接口 | 限制 | 超限响应 |
|---|---|---|
| 开始问诊（创建会话） | 5 次/小时/IP | 429 + 4301 |
| 音频上传 | 受业务轮次约束（≤10 轮/会话）+ 单文件 ≤5MB、≤60s；Nginx 该 location 单独更严 zone | 429 / 201x |
| 医生登录 | 10 次/分钟/IP | 429 + 4301 |
| 全局静态资源 | Nginx 兜底速率 | 503 |

补充：音频上传校验扩展名/MIME 白名单 + 文件头魔数 + 大小/时长上限（格式结论以 R4 微信音频调研为准）；上传文件名一律服务端生成 UUID，拒绝客户端可控路径拼接。

### 5.6 输入校验与其他基线

- 所有入参过 Pydantic v2 强类型模型并设长度上限；就诊号 `^[0-9]{1,6}$`（PRD：纯数字大键盘录入）。患者端除音频外无自由文本输入，天然缩小注入面，但仍须对就诊号等字段做正则白名单校验。
- SQL 全部参数化查询（repos 层统一），杜绝字符串拼 SQL。
- 进程以专用低权用户（systemd `User=zhongyi`）运行；SQLite 文件与 env 文件权限 600；`pip-audit` 纳入发布前检查。
- HTTPS 已具备（备案域名），HTTP 80 仅做 301 跳转。

## 6. 数据备份与恢复（SQLite 场景）

### 6.1 最佳实践要点

- **禁止直接 cp/vm 快照正在运行的 SQLite 库**：可能拷到不一致状态。官方提供两种在线一致快照方式 [来源: sqlite.org]：
  1. **Online Backup API**（Python `conn.backup(dst)` 或 CLI `.backup`）：完成时目标文件是拷贝开始时刻的一致快照，源库仅在读取瞬间短暂加锁，业务无感；
  2. **`VACUUM INTO 'file'`**：事务性一致快照，产物已压缩清理、体积更小，但需约 2 倍库大小剩余磁盘，且中断可能留下不完整文件（`synchronous=NORMAL/FULL` 下完成时有 fsync 保护）。
- **备份三要素**：定期（自动化定时任务）、异地（另一介质/机房）、可验证（定期恢复演练，没演练过的备份等于没有备份）。
- 本库规模极小（首年 ≤10 万条记录，几百 MB 以内），全量日备完全够用，不需要 WAL 归档级方案。

### 6.2 对本项目的落地建议

- **每日全量**：systemd timer（03:00 低峰，`Persistent=true` 补跑错过的触发）执行 `scripts/backup.sh`：
  1. `sqlite3 $DB_PATH ".backup /tmp/xx.db"`（或 Python backup API）；
  2. 对副本执行 `PRAGMA integrity_check;` 必须 ok，否则告警；
  3. gzip 为 `backups/zhongyi-YYYYMMDD.db.gz`；
  4. 本地保留 **30 天滚动**（`find -mtime +30 -delete`）。
- **每周异地一份**：周日备份额外加密（`openssl enc -aes-256-cbc -pbkdf2` 或 age 公钥加密——备份含病情摘要属敏感数据）后推送阿里云 OSS（ossutil/rclone）或 rsync 至第二台机器；OSS Bucket 设版本化与生命周期。
- **完整性哨兵**：backup.sh 结束比对备份体积与前一日偏差 >50% 时输出 WARNING（防静默空备份）。
- **恢复演练**：提供 `scripts/restore.sh`（解压 → integrity_check → 替换库文件 → systemctl restart zhongyi → curl /readyz），验收标准：任取一份历史备份能在 15 分钟内恢复出可用系统；上线前必须实练一次。
- **保留期清理任务**：另一个 systemd timer（04:00）执行 cleanup.sh：清理过期备份、轮转压缩 90 天前日志、清扫音频临时目录中 >1 小时的残留文件（正常流程不留存录音，此为兜底清扫，防止异常中断遗留临时文件）。
- WAL 模式配套：`PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` 常设，备份 API 自身能正确处理 WAL，无需先 checkpoint。

## 7. 部署形态

### 7.1 标准组合与拓扑

```
患者H5 / 医生后台浏览器
        │ HTTPS 443
        ▼
      Nginx ──── 静态前端 web/dist（SPA try_files 回退 index.html）
        │ /api/ 反代 127.0.0.1:8000
        ▼
gunicorn -w 2（UvicornWorker）→ FastAPI app → SQLite(WAL) + logs/
   ↑ systemd zhongyi.service（Restart=always）
   ↑ systemd timers（backup / cleanup）
```

### 7.2 systemd 服务单元（模板）

```ini
# deploy/zhongyi.service
[Unit]
Description=Zhongyi pre-consultation API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=zhongyi
Group=zhongyi
WorkingDirectory=/opt/zhongyi/app
EnvironmentFile=/opt/zhongyi/env
ExecStart=/opt/zhongyi/venv/bin/gunicorn app.main:app \
    -k uvicorn.workers.UvicornWorker -w 2 \
    -b 127.0.0.1:8000 --timeout 120 --graceful-timeout 30 \
    --worker-tmp-dir /dev/shm
KillSignal=SIGTERM
TimeoutStartSec=60
TimeoutStopSec=45
Restart=always
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/opt/zhongyi/data /opt/zhongyi/logs

[Install]
WantedBy=multi-user.target
```

参数依据与陷阱（均已核实官方文档）：

- gunicorn 收到 SIGTERM/SIGQUIT 后给 worker `--graceful-timeout`（默认 30s）完成存量请求，超时才 SIGKILL；uvicorn 自身的优雅停机默认仅 **3 秒**，长请求（音频上传+AI 摘要可达数十秒）场景必须显式调大 `timeout_graceful_shutdown`。
- systemd 停服链路为 SIGTERM → `TimeoutStopSec` → SIGKILL，因此 **TimeoutStopSec(45) 必须大于 graceful-timeout(30)**，否则优雅停机形同虚设；`TimeoutStartSec` 要容纳慢导入。
- 不要用 shell 包装脚本启动（KillMode 只杀 shell 不杀 gunicorn）；确需包装须 `exec` 或 `KillMode=control-group`。
- workers=2 足够（日 500 次），SQLite 写并发靠 WAL + busy_timeout=5000 兜底；`--timeout 120` 覆盖最长的"上传+AI 生成"请求。

### 7.3 Nginx 配置要点

```nginx
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;

server {
    listen 443 ssl http2;
    server_name your.domain.cn;
    # ssl_certificate ...; ssl_certificate_key ...;
    client_max_body_size 10m;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "microphone=(self)" always;

    root /opt/zhongyi/web/dist;
    location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; }
    location = /index.html { add_header Cache-Control "no-cache"; }
    location / { try_files $uri /index.html; }

    location /api/ {
        limit_req zone=perip burst=20 nodelay;
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 130s;   # > app --timeout 120
        proxy_send_timeout 60s;
    }
}
server { listen 80; return 301 https://$host$request_uri; }
```

### 7.4 健康检查与优雅停机

- `GET /healthz`（存活/liveness）：不查依赖，返回进程活着；供云监控拨测与 `deploy.sh` 发布确认。
- `GET /readyz`（就绪/readiness）：执行 `SELECT 1` 验证 DB 可读写 + data 目录磁盘余量 > 阈值；失败返回 503。
- 优雅停机验证项：`systemctl restart` 期间进行中的问诊提交能完成、新请求被 Nginx 排队或快速失败后重试、无半截事务。

### 7.5 发布与回滚

`scripts/deploy.sh` 幂等步骤：备份当前库 → 取代码（git checkout 发布 tag）→ `venv/bin/pip install -r requirements.lock` → 应用未执行的 migrations → `systemctl restart zhongyi` → 循环 curl /readyz 直至通过，失败即报错退出。回滚 = checkout 上一 tag + 重启（迁移脚本必须向后兼容一版，见第 9 章）。空白服务器初始化步骤（装 nginx/python3.11/建用户建目录/env/systemd enable --now）固化到 `docs/deploy.md` 清单。

## 9. 可移植性红线落实方式

### 9.1 最佳实践要点

可移植性的敌人是四类隐式耦合：**环境耦合**（解释器/依赖版本漂移）、**路径耦合**（cwd/绝对路径假设）、**时间耦合**（naive datetime 与服务器时区）、**结构耦合**（手工改 schema 无法在新机器重建）。逐条给出红线：

### 9.2 对本项目的落地建议

1. **依赖与运行时锁定**：`requirements.lock` 由 pip freeze 生成、精确到 patch 版本；README 固定 Python 小版本（建议 3.11.x）并写入 `.python-version`；venv 隔离安装；发布机与开发机版本不一致视为环境不合法。
2. **路径处理**：`BASE_DIR = Path(__file__).resolve().parents[1]` 作为唯一路径锚点；数据/日志/备份目录 = `BASE_DIR` 下相对段且可被 `DATA_DIR`/`LOG_DIR` 环境变量重定位；全面 pathlib，禁 `os.getcwd()`、禁字符串拼路径、禁硬编码盘符与家目录；文件读写显式 `encoding="utf-8"`。
3. **时区处理**：
   - 存储层一律 UTC（ISO8601 带偏移字符串或 unix 秒）；
   - 业务时区常量 `BUSINESS_TZ = ZoneInfo("Asia/Shanghai")`："当日就诊号""今日列表"等业务日界用它计算，绝不用服务器本地时钟直觉；
   - 对外 API 返回带 `+08:00` 的 ISO8601，前端只负责展示；服务器 `timedatectl set-timezone Asia/Shanghai`；日志时间戳带偏移量。
4. **Schema 版本化迁移**：`migrations/001_init.sql` 起顺序编号，库内置 `schema_migrations` 表登记已应用版本；deploy 时补跑未应用脚本；**每条迁移必须向后兼容一版**（先加列后删列），保证回滚旧代码仍能读写新库。
5. **平台差异清单**：开发可能在 Windows、生产必为 Linux——pathlib 屏蔽分隔符差异；信号驱动的优雅停机仅在 Linux 生效（Windows 开发时降级容忍）；shell 脚本只跑在服务器。
6. **一键可移植验收标准**：拿一台空白 Ubuntu/Debian ECS，按 `docs/deploy.md` 从零操作 ≤1 小时内 `/readyz` 通过、一次完整问诊流程走通——以此作为移植性红线的最终检验。

## 10. 本项目工程准则清单（E1–E24）

以下为后续设计与开发直接引用的硬性规则。凡与代码现状冲突处，以本清单为准整改。

**架构与代码组织**
- **E1** 代码严格按 api/schemas/services/repos/models/core 六层组织；路由层禁止出现 SQL 与业务判断，SQL 只存在于 repos 层。
- **E2** 依赖方向单向向下（api→services→repos），禁止反向引用与循环依赖；ASR/LLM 第三方客户端必须封装为可注入接口。

**配置管理**
- **E3** 所有环境相关配置仅经 pydantic-settings 从环境变量/.env 读取；启动时 fail-fast 校验必填项；禁止代码中出现硬编码密钥、IP、绝对路径。
- **E4** `.env` 入 .gitignore，仓库只提交 `.env.example`；SECRET_KEY 等密钥用 `openssl rand -hex 32` 生成；生产密钥文件权限 600。

**日志**
- **E5** 生产日志为 JSON 结构化 + DEBUG/INFO/WARNING/ERROR 四级；每请求由中间件生成 trace-id，贯穿全部日志并回填响应头 `X-Request-ID` 与错误响应体。
- **E6**【红线】日志禁止包含音频内容、逐字转写、病情摘要正文、患者身份信息；就诊号打印必须经 `mask_visit_no()` 脱敏（≤2 位全星号；3–5 位留首末各 1 位；>5 位留前 2 后 2），排查统一用 record_id 关联；密钥/Cookie 不落日志。
- **E7** 审计日志独立文件（登录成败、登出、医生查看详情、删除、解锁），JSON 行，保留 ≥180 天。

**异常与错误码**
- **E8** 全局异常处理器兜底一切未捕获异常；对外统一 `{code,message,data,traceId}` 格式，HTTP 状态码语义正确；堆栈只进日志不下发。
- **E9** 业务错误码按千位分段（1xxx 系统/2xxx 参数/3xxx 认证/4xxx 业务/43xx 频控/5xxx 第三方），唯一权威表在 `docs/error-codes.md`，新增必须登记。

**安全**
- **E10** 医生后台认证采用服务端 Session（opaque token 存库，Cookie HttpOnly+Secure+SameSite=Lax），30 分钟滑动过期，登出即销毁；不使用 JWT。患者端用一次性问诊凭证，服务端校验。
- **E11** 密码仅存 Argon2id 哈希（m≥19MiB, t≥2, p=1；argon2-cffi），次选 bcrypt cost≥12；禁止 MD5/SHA 系与可逆加密。
- **E12** 登录连续失败 5 次锁定 15 分钟（计数挂账号维度）+ 登录接口 IP 限流 10 次/分钟；失败提示不泄露账号存在性；每次失败写审计日志。
- **E13** Nginx 统一输出安全响应头（HSTS/nosniff/X-Frame-Options/CSP/Referrer-Policy）；Permissions-Policy 必须允许患者页 `microphone=(self)`；含摘要数据的 API 响应 `Cache-Control: no-store`。
- **E14** 患者端无登录接口双层限流：Nginx per-IP 兜底 + slowapi 精细（开始问诊 5 次/h/IP；登录 10 次/min/IP；超限 429+4301）；音频上传限 ≤5MB、≤60s、≤10 轮，并校验 MIME+魔数。
- **E15** 全部入参 Pydantic 强校验并设上限（就诊号 `^[0-9]{1,6}$`）；SQL 全参数化；上传文件名服务端生成，禁止客户端可控路径。
- **E16** 服务以专用低权用户运行（systemd User=zhongyi），SQLite/env 文件权限 600；发布前跑 pip-audit。

**数据备份与清理**
- **E17** SQLite 备份只用在线备份 API 或 VACUUM INTO，禁止 cp 运行库；每日 03:00 timer 全量备份 + integrity_check，本地保留 30 天滚动，每周一份加密传异地（OSS/第二台机器）。
- **E18** restore.sh + 恢复演练为上线验收必要条件（任取历史备份 15 分钟内恢复可用）；cleanup timer 负责过期备份清理、90 天前日志归档、临时音频目录 >1h 残留清扫。

**部署**
- **E19** 标准部署形态固定为 systemd(Restart=always) + gunicorn(UvicornWorker, w=2, graceful-timeout 30) + Nginx(443 TLS/静态托管//api 反代)；TimeoutStopSec(45) > graceful-timeout(30) > uvicorn 优雅停机窗口；app --timeout 120 < proxy_read_timeout 130s。
- **E20** 提供 `/healthz`（存活）与 `/readyz`(DB+磁盘就绪) 双探针；发布走幂等 deploy.sh：备份→切 tag→装锁定依赖→迁移→重启→readyz 确认；失败可回滚上一 tag（迁移向后兼容一版）。

**测试**
- **E21** tests/unit 与 tests/integration 分离；集成测试每例独立 tmp_path SQLite + dependency_overrides 注入 Fake ASR/LLM；`APP_ENV=test` 机制性禁止真实外呼；时间逻辑用注入 clock/freezegun，禁 sleep。
- **E22** pytest --cov 一键执行作为发版前置检查；core/services 覆盖率 ≥80%、总体 ≥70%；必测点：脱敏函数、登录锁定、错误码映射、限流触发、trace-id 贯穿。

**可移植性**
- **E23** requirements.lock 锁精确版本 + Python 小版本固定（3.11.x）；路径一律基于 BASE_DIR 的 pathlib 相对推导，可经 DATA_DIR/LOG_DIR 重定位，禁 cwd/硬编码路径，读写显式 utf-8。
- **E24** 数据库时间统一存 UTC，业务日界用 Asia/Shanghai 计算，API 返回带 +08:00 的 ISO8601；schema 变更只经 migrations/ 编号脚本（登记到 schema_migrations），禁止手工改生产库结构。
