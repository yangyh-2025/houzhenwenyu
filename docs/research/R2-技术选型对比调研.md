## 0. 结论速览

**最终推荐栈：FastAPI（最新主线，最低要求恰为 Python 3.9）+ SQLite(WAL) + SQLAlchemy 2.0 + Vue 3 + Vite（显式降 target）+ AudioWorklet/ScriptProcessorNode 采集 PCM16K WAV + audio 元素队列播放 TTS。**

核心判断依据（详见各章）：

1. **Django 被排除的决定性原因**：Python 3.9 只能配 Django 4.2 LTS，而其扩展支持已于 **2026-04-07 终止**（今天已过期），不再有安全更新。
2. **MediaRecorder 方案被排除的决定性原因**：iOS 微信（WKWebView/Safari）的 MediaRecorder **只出 audio/mp4(AAC)**，Android 出 webm/opus——服务端必然要面对两种容器格式的转码，ffmpeg 依赖无法回避，与本机无 ffmpeg、生产零依赖的约束直接冲突。
3. **SQLite 完全够用**：日均 ≤500 会话的写入量对 WAL 模式而言低两个数量级，省掉 PostgreSQL 的常驻运维成本。

## 一、后端框架：FastAPI vs Flask 3.x vs Django 4.x/5.x

### 1.1 Python 3.9 兼容边界（已核实）

| 框架 | 对 Python 3.9 的支持现状 | 关键事实 | 来源 |
|---|---|---|---|
| **Django** | ⚠️ 仅 4.2 LTS，且**已 EOL** | Django 5.0 起要求 Python ≥3.10；官方 FAQ 明确"Python 3.9 安全支持于 2025-10 结束、Django 4.2 LTS 安全支持于 **2026-04-07 结束**，因此 Django 4.2 是最后支持 3.9 的版本"。截至本报告日（2026-08-24），在 Python 3.9 上运行 Django 已**无任何受安全支持的版本**。Django 5.2 LTS 支持 3.10–3.14，Django 6.0 要求 ≥3.12 | [Django 安装 FAQ](https://docs.djangoproject.com/en/4.2/faq/install/)、[Django 下载页](https://www.djangoproject.com/download/) |
| **Flask** | ✅ 3.1.x 支持 ≥3.9 | Flask 3.1.0（2024-11-13）弃 3.8，最低 3.9；最新补丁 3.1.3（2026-02-18）。注意：changelog 中未发布的 **3.2.0 已计划弃 3.9**（升到 3.10），届时需 pin `<3.2` | [Flask Changes](https://flask.palletsprojects.com/en/stable/changes/)、[PyPI Flask 3.1.0](https://pypi.org/project/Flask/3.1.0/)、[安装文档](https://flask.palletsprojects.com/en/stable/installation/) |
| **FastAPI** | ✅ 最新主线仍支持 3.9 | 0.125.0（2025-12-17）弃 3.8 后，**最低要求恰好是 3.9**，即当前最新版可直接装在开发机的 3.9.11 上，无版本惩罚 | [FastAPI 0.125.0 Release](https://github.com/fastapi/fastapi/releases/tag/0.125.0)、[Release Notes](https://fastapi.tiangolo.com/release-notes/) |

配套库的边界（同样影响依赖 pin）：

- **Uvicorn**：0.40.0（2025-12-21）起弃 Python 3.9。3.9 下 pip 会按 `Requires-Python` 元数据自动落到 0.39.x，但 requirements 中建议显式写 `uvicorn>=0.30,<0.40`。来源：[Uvicorn Release Notes](https://www.uvicorn.org/release-notes)
- **Pydantic v2**：最新发布版 2.13.x 仍要求 ≥3.9；main 分支已声明 `requires-python>=3.10`，下一代将弃 3.9，建议锁 `pydantic<3` 并关注升级公告。来源：[pydantic/pyproject.toml](https://github.com/pydantic/pydantic/blob/main/pyproject.toml)
- SQLAlchemy 2.0 / httpx / Alembic 对 Python 3.9 均长期兼容，无版本惩罚。

### 1.2 能力对比

| 维度 | FastAPI（+Uvicorn） | Flask 3.1 | Django 4.2 |
|---|---|---|---|
| 异步模型 | 原生 ASGI，`async def` 路由 + `httpx.AsyncClient` 天然并发等待外部大模型/TTS 长调用，可做 SSE 流式转发 | WSGI 同步为主；虽支持 `async def` 视图但经 asgiref 模拟、仍在 WSGI 服务器上跑，长调用会占死 worker，需 gunicorn 线程池/gevent 缓解 | 有 ASGI 支持，但 3.9 下只能用已 EOL 的 4.2 |
| 外部 AI API 长等待场景（单次问答等待可达数十秒） | ★ 最优：协程挂起几乎零成本，单进程即可承载数十路等待 | 差：每路等待独占一个 worker/线程，并发=线程数 | 同 Flask |
| 自动 API 文档 | 内置 Swagger UI / ReDoc（OpenAPI 由类型注解自动生成），前后端联调成本低 | 需 flasgger / APIFlask 等扩展 | 需 DRF + drf-spectacular |
| 请求校验 | Pydantic v2 类型级校验 + 自动错误响应，最适合"音频 base64 + 结构化症状字段"这类混合载荷 | 手工校验或引入 marshmallow/pydantic（等于自己拼一个 FastAPI） | DRF Serializer，较重 |
| 学习/运维成本 | 低—中：概念少（路由/依赖注入/Pydantic），单文件即可起步 | 最低，但补齐异步+文档+校验后总成本反超 | 最高：全家桶（ORM/Admin/Auth/模板）；Admin 是唯一亮点 |
| 医生端后台适配 | 自研移动页或 SQLAdmin 类方案 | 同左 | Django Admin 省力，但被"EOL 无安全更新"一票否决 |

### 1.3 推荐

**推荐 FastAPI。** 理由：

1. 版本兼容性最优：当前主线版本最低要求恰好是 Python 3.9，不受"用旧版换兼容"的惩罚（Flask 即将面临 3.2 弃 3.9 的 pin 问题，Django 直接无安全版本可用）。
2. 与本项目最重的负载特征——**等待外部大模型/TTS 接口数十秒返回**——精确匹配：async 协程等待不占线程，单机单进程即可高并发挂起；且便于向患者端做 SSE 流式输出。
3. Pydantic v2 校验 + 自动 OpenAPI 文档，显著降低前后端联调与医生端接口维护成本。

依赖锚点建议：`fastapi>=0.125`、`uvicorn>=0.30,<0.40`、`pydantic>=2,<3`、`sqlalchemy>=2.0`、`httpx>=0.27`、`alembic`。

## 二、数据库：SQLite(WAL 模式) vs PostgreSQL

### 2.1 容量与并发评估（按业务假设）

假设：日均 ≤500 会话，首年 ≤10 万条记录量级，早高峰集中并发写入。

- **容量测算**：500 会话/日 × 365 天 ≈ 18 万会话行/年；即使按每会话 10 轮问答展开为消息表，约 180 万行/年、单行 ~1KB，年增 <2GB。SQLite 官方支撑容量至 TB 级，该量级**余量超过两个数量级**。
- **早高峰并发写**：WAL 模式下"**单写者 + 多读者并行**"，读者不阻塞写者；写者之间串行，但每次问诊提交的写事务是毫秒级短事务，即便峰值 100 人同时在线，同一毫秒冲突撞写的概率也很低，配合 `busy_timeout` 重试即可兜底。SQLite 官方明确"WAL 不会让写变并发，但读写在 WAL 下互不阻塞"。来源：[SQLite WAL 文档](https://www.sqlite.org/wal.html)
- 结论：**两者在该容量下都足够，差异不在能力而在运维成本。**

### 2.2 运维成本对比

| 维度 | SQLite(WAL) | PostgreSQL |
|---|---|---|
| 部署 | 单文件、零服务进程、零配置 | 常驻守护进程，占用数百 MB 内存，需账号/端口/pg_hba 配置 |
| 备份 | `VACUUM INTO` 一条 SQL 出一致性副本（≥3.27，官方称"最安全的备份方式"），cron + 异机拷贝即完成 | pg_dump / WAL 归档 / base backup，策略复杂度高一级 |
| 清理 | DELETE + 低峰 VACUUM；`wal_checkpoint(TRUNCATE)` 回收 -wal 文件 | autovacuum 自动，但调优有学习成本 |
| 升级/监控 | 换个文件的事 | 大版本升级需 dump/restore 或 pg_upgrade |
| 适用边界 | 单机、写吞吐中低——本项目完全命中 | 多实例部署、重报表分析、中文全文检索（pg_jieba）、高频并发写 |

**推荐：SQLite(WAL) 起步。** 单台 Linux 服务器 + 该量级，PostgreSQL 属于过度设计；同时按下述方法保留迁移通道。

### 2.3 SQLite WAL 配置要点

```python
# app/db.py —— PRAGMA 全部集中在这一处，便于未来整体替换为 PG 连接工厂
from sqlalchemy import event, create_engine
from sqlalchemy.engine import Engine

@event.listens_for(Engine, "connect")
def _set_sqlite_pragma(dbapi_conn, _):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA journal_mode=WAL")     # 写前日志：读写并行
    cur.execute("PRAGMA busy_timeout=5000")    # 默认0ms会立刻SQLITE_BUSY，给5s自旋重试
    cur.execute("PRAGMA synchronous=NORMAL")   # WAL下安全，只在checkpoint时fsync
    cur.execute("PRAGMA foreign_keys=ON")
    cur.close()

engine = create_engine("sqlite:///data/app.db", pool_pre_ping=True)
```

要点说明（来源：[pragma 文档](https://www.sqlite.org/pragma.html#pragma_busy_timeout)、[WAL 文档](https://www.sqlite.org/wal.html)）：

1. **并发写行为**：任一时刻仅一个写事务；其余写者靠 busy_timeout 自旋等待。写事务必须短——**严禁在事务内调用大模型/TTS 等慢接口**，应先提交会话记录再发起外部调用。
2. 用 `BEGIN IMMEDIATE` 发起写事务可减少"读升级写"导致的 `SQLITE_BUSY_SNAPSHOT` 死锁型失败（busy_timeout 对此类无效）。
3. `-wal`/`-shm` 文件须与主库同目录同主机（共享内存要求），数据库目录不要放网络文件系统。
4. 长期挂起的读事务会阻止 checkpoint 导致 -wal 无限膨胀，ORM 层避免长事务、及时 commit/rollback。
5. 定期（每日备份后低峰期）执行 `PRAGMA wal_checkpoint(TRUNCATE)`；如需回收空间执行 `VACUUM`（全库排他锁，避开门诊高峰）。
6. `auto_vacuum` 若要用必须在建库前设置；否则清理以 DELETE+手动 VACUUM 为准。

**备份命令**（cron 每日凌晨）：

```bash
# 官方推荐的一致性热备：VACUUM INTO（源库持续可用，产物紧凑且经过整理）
sqlite3 /srv/app/data/app.db "VACUUM INTO '/srv/backup/app-$(date +%F).db'"
# 校验备份有效性
sqlite3 "/srv/backup/app-$(date +%F).db" "PRAGMA integrity_check;"
# 异机异地拷贝 + 保留 N 天轮转
```

### 2.4 ORM 层保留切换 PostgreSQL 的可能（SQLAlchemy 守则）

1. 全部 DDL/DML 经 SQLAlchemy ORM + Alembic 迁移，禁止 SQLite 方言特有 SQL（`PRAGMA` 仅出现在上面单一工厂模块内）。
2. 列类型只用通用类型：`String/Text/Integer/Float/LargeBinary/DateTime/JSON`；JSON 字段用 `sa.JSON`（PG 下自动映射，必要时换 `postgresql.JSONB` variant，一行改动）。
3. 时间统一存 UTC，避免 SQLite 无时区类型带来的语义漂移。
4. 主键用 `Integer` 自增，两端通用；不用 SQLite 的 `AUTOINCREMENT` 关键字特性。
5. 连接串走配置（`sqlite:///...` ↔ `postgresql+psycopg://...`），Alembic 对 SQLite 的 ALTER 局限启用 batch mode，迁移脚本保持方言中立。
6. 触发迁移的量化条件（预先写进运维文档）：busy 错误率异常上升、需要多应用实例共享库、出现中文分词检索等 PG 特性需求。

## 三、前端工程化：Vue 3 + Vite vs React + Vite vs 无构建原生 ES 模块

### 3.1 目标运行环境分析

- **Android 微信**：老设备/新装微信可能仍带旧 TBS 内核（历史上基于 Chromium 57~77），新内核为 XWeb（现代 Chromium 系，随微信自动更新）。腾讯云官方 FAQ 明确：**旧内置内核不支持 getUserMedia，XWeb 内核才支持设备采集**，且强制 HTTPS。来源：[TRTC 微信 H5 FAQ](https://web.sdk.qcloud.com/trtc/webrtc/v5/doc/zh-cn/tutorial-06-info-faq.html)、[微信开放社区](https://developers.weixin.qq.com/community/develop/doc/0006caccaac77063a9517361863c00)、[微信开发者兼容性文档](https://dev.weixin.qq.com/docs/analysis/compatibility.html)
- **iOS 微信**：使用系统 WKWebView，能力等同对应版本的 iOS Safari（getUserMedia 需 iOS 14.3+）。
- **构建产物语法红线**：Vite 7 起 `build.target` 默认值改为 `baseline-widely-available` = **chrome107/safari16**（更新的大版本甚至 chrome111/safari16.4），旧默认 `modules` 也是 chrome87/safari14——**两者都高于旧 X5/TBS 内核**，可选链 `?.`、空值合并 `??` 等语法将直接白屏。**必须显式覆盖 target**。来源：[Vite 7 公告](https://vite.dev/blog/announcing-vite7)、[build-options 文档](https://vite.dev/config/build-options)、[vitejs/vite#20007](https://github.com/vitejs/vite/issues/20007)

### 3.2 三方案对比

| 维度 | Vue 3 + Vite | React + Vite | 无构建原生 ES 模块 |
|---|---|---|---|
| 旧内核兼容路径 | 显式 `build.target:'es2018'`（Vue 运行时仅需 Proxy，Chromium 49+/Safari 10+ 即可）+ 按需 core-js polyfill；极端旧内核可加 @vitejs/plugin-legacy 兜底 | 同左（React 18/19 运行时同样可行） | **致命伤：没有构建链就没有转译环节**，代码必须全程手写 es2018 以下语法并手工管理 polyfill 与 importmap，长期纪律成本极高 |
| 组件化/状态管理 | Composition API + `reactive/ref` 对"录音状态机""TTS 队列"这类状态密集逻辑表达自然；`<script setup>` 单文件组件粒度合适 | JSX + hooks 表达力相当 | 状态密集 UI 全靠手写 DOM diff/事件绑定，代码量翻倍 |
| 生态与团队效率 | 中文文档/社区资料最丰富，移动端组件库（Vant 等）成熟，适老化定制组件参考案例多 | 生态强但中文医疗 H5 场景案例相对少 | 无依赖、加载最快，但开发效率最低 |
| 构建链复杂度 | Vite 一条命令，Node v24.13.1 完全满足（Vite 5 要求 Node 18+，Vite 7 要求 20.19+） | 相同 | 零构建 |
| 产物体积 | gzip 后框架运行时约 30–40KB，H5 场景可接受 | 相近略大 | 最小 |

自定义组件实现友好度（自绘数字键盘 / 录音状态机 / TTS 播放队列）：三者在能力上都能实现，差别在表达成本。录音状态机（idle→recording→uploading→result→error）与 TTS 队列（pending→playing→paused）都是典型的"有限状态 + 副作用"场景，Vue 的组合式函数（composable）可以把状态机封装成 `useRecorder()` / `useTtsQueue()` 独立模块，视图层只绑定状态，测试与复用都干净；无构建方案下同样的逻辑要与 DOM 操作耦合，改动风险大。

### 3.3 推荐

**推荐 Vue 3 + Vite**，配置要点：

```js
// vite.config.js —— 关键是显式压低 target，覆盖默认的 chrome107
export default defineConfig({
  build: {
    target: 'es2018',          // 语法层兼容旧 X5/XWeb（Chromium 66+）
    cssTarget: 'chrome61',
  },
});
```

- 不默认引入 @vivejs/plugin-legacy 双包构建；仅当真机矩阵发现 Chromium <61 级别的残留设备时再加（XWeb 已普遍 ≥86）。用到的少数新 API（如 `Promise.allSettled`、`ResizeObserver`）按需手引 core-js 单个 polyfill。
- 患者端不引重型 UI 库（适老化界面本身就要大字号大按钮全自绘）；医生端列表页可选轻量组件库。
- 锁定 `vite@5.4.x`（或 6.x）+ `@vitejs/plugin-vue`，Node v24.13.1 满足其引擎要求。

## 四、浏览器录音采集方案对比（关键技术点）

### 4.0 共同前提：getUserMedia 在微信内的可用性

两个方案都依赖 `navigator.mediaDevices.getUserMedia`，其可用性是第一道闸门（详见 R4 微信语音专项）：

- Android 微信：**XWeb 内核支持**；老 TBS/未完成 XWeb 安装的微信完全没有该 API（静默失败）。首次装微信需在 Wi-Fi 下等待 XWeb 自动装好。
- iOS 微信：WKWebView，iOS 14.3+ 支持。
- 强制 HTTPS；iframe 需 `allow="microphone"`。
- 最大兼容兜底是微信 JS-SDK `wx.startRecord/uploadVoice`（产出 amr/silk，服务端处理反而更麻烦），作为预案保留。

### 4.1 两方案对比

| 角度 | 方案A：MediaRecorder(webm/opus) + 服务端转码 | 方案B：WebAudio 采集原始 PCM → JS 重采样 16k 单声道 → WAV → base64 |
|---|---|---|
| **兼容性** | Android XWeb：✅ webm/opus。**iOS 微信（WKWebView）：Safari 14.5+ 才有 MediaRecorder，且只接受 `audio/mp4`(AAC)，拒绝 webm/opus**；opus-in-mp4 要 iOS 17+。→ 服务端将收到 mp4/AAC 与 webm/opus 两种格式 | getUserMedia 可用性同左；AudioContext 全线支持；**AudioWorklet：Chrome 66+/Safari 14.1+(iOS 14.5)+**，XWeb（Chromium 86+）完全覆盖；更老的 TBS 内核走 ScriptProcessorNode 降级（规范已废弃但全线可用） |
| **可控性** | 输出容器/编码由浏览器决定（通常 48kHz），采样率、声道不可控；静音检测需另挂 AnalyserNode 并行处理；时长控制粗糙 | **完全可控**：强制 16kHz 单声道 s16 PCM，与主流大模型音频输入格式（pcm/wav 16k）直接对齐；能量阈值 VAD 在同一音频回调内同步完成；可精确控制分段时长 |
| **服务端依赖** | ❌ 必须解码 mp4/AAC + webm/opus 两种容器 → **ffmpeg 不可避免**（纯 Python 解码 AAC/mp4 不现实）。与本机无 ffmpeg、生产零依赖硬约束直接冲突 | ✅ 零依赖：上传即是大模型要的 WAV(base64)，后端透传即可 |
| 数据量 | opus 压缩率最高（~24kbps 级） | 16k×16bit = 32KB/s，60 秒约 1.9MB，base64 后 ~2.5MB——H5 上传完全可接受 |

来源：[caniuse MediaRecorder](https://caniuse.com/mediarecorder)、[Safari MediaRecorder MIME 限制](https://stackoverflow.com/questions/66902406/which-mime-types-are-supported-by-mediarecorder-on-safari)、[WebKit Opus-in-MP4（iOS 17+）](https://bugs.webkit.org/show_bug.cgi?id=282220)、[caniuse AudioWorklet](https://caniuse.com/mdn-api_audioworklet)、[Chrome AudioWorklet 发布博客（ScriptProcessorNode 废弃原因）](https://developer.chrome.com/blog/audio-worklet)、[MDN AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet)

### 4.2 AudioWorklet 在 X5/XWeb 的可用性与降级路径

```
特性检测：'audioWorklet' in audioContext
├── 是（XWeb 及所有现代内核）→ addModule(worklet代码URL) → AudioWorkletNode
│     采集在独立音频线程，主线程零卡顿，适合长时间录音
└── 否（极老 TBS ≤Chromium65 等）→ createScriptProcessorNode(4096, 1, 1)
      主线程回调，注意 UI 卡顿；录音时长限制在分钟级可控
```

两条路径统一封装为 `RecorderEngine` 接口（start/stop/onChunk），上层状态机无感。降级链：`AudioWorklet → ScriptProcessorNode → （终极）JSSDK wx.startRecord 预案`。

### 4.3 推荐：方案 B

理由：① 服务端零 ffmpeg 依赖，直出大模型要求的 16k WAV/base64；② 采样率/声道/VAD 全可控，适老化的静音超时自动结束依赖它；③ 兼容面经 ScriptProcessorNode 降级后覆盖全部微信内核；④ MediaRecorder 在 iOS 上连格式都无法统一，方案 A 的服务端转码成本不可回避。

实现要点：AudioWorklet 线程内累积 Float32 帧 → 主线程批量取回 → 下采样（线性插值或抽取滤波）至 16k → 交错为 Int16 → 拼 RIFF/WAVE 头（44 字节）→ `FileReader.readAsDataURL` 得 base64 → POST。停止录音后及时 `disconnect` 并关闭流轨释放麦克风指示灯。

## 五、TTS 音频播放

### 5.1 audio 元素 vs WebAudio 解码播放

| 维度 | `<audio>` 元素 | WebAudio decodeAudioData |
|---|---|---|
| 加载模型 | 流式，src 给 URL 即边下边播 | 需完整下载整段再解码，整段 PCM 驻留内存 |
| 音量/倍速 | volume / playbackRate 均支持 | 更精细（增益节点、精确调度） |
| iOS 兼容坑 | 手势解锁一次即可；blob/objectURL 正常；**不受物理静音键影响** | AudioContext 需 resume；**iOS 物理静音键会让 Web Audio 无声**（audio 元素不受影响）；后台切换会被再挂起 |
| 实现成本 | 低 | 中 |

医疗问答 TTS 都是数秒短句，无需采样级调度。**推荐以 `<audio>` 元素为主**；WebAudio 只用于解锁技巧与（可选的）播放波形动画。这也顺带规避了静音键坑。来源：[unmute-ios-audio](https://github.com/feross/unmute-ios-audio)

### 5.2 用户手势解锁播放链的实现模式（iOS/微信关键坑）

iOS 规则（来源：[iOS audio unlock 实测笔记](https://js2devlog.com/en/devlog/ios-safari-audio-unlock)、[silent-wav 解锁技巧](https://www.flowy.fm/learn/ios-safari-audio-unlock-trick)、[SO: Cannot resume AudioContext in Safari](https://stackoverflow.com/questions/57510426/cannot-resume-audiocontext-in-safari)、[Matt Montag boilerplate](https://www.mattmontag.com/web/unlock-web-audio-in-safari-for-ios-and-macos)）：

1. `AudioContext.resume()` 与 `audio.play()` **必须发生在用户手势事件的同步调用栈内**——放进 Promise/`setTimeout`/框架的 effect 里即被视为自动播放而拦截（Chrome/Firefox 无此限制）。
2. 解锁动作：在"开始预问诊"按钮的 click/touchend 回调里同步执行——创建 AudioContext 并 `resume()`；同时让全局唯一的 `<audio>` 元素播放一个 ~16 字节静音 WAV data-URI 并 `play()` 成功一次，此后该页面会话内程序化换 src 再 play 不再需要手势。
3. 细节坑：`pointerdown` 可能不算手势，用 `touchend`/`click`；解锁 promise 被 reject 时不得置位 unlocked 标记（下次交互重试）；回到前台 `visibilitychange` 里重新 `resume()`；来电/闹钟中断后暂停队列并在可见性恢复时续播。

### 5.3 连续多段 TTS 队列设计

```
segments[] + 游标 i：
play(i): audio.src = objectURL(blob[i]); await audio.play()
         └ playing 期间并行 prefetch(i+1)：fetch→Blob→objectURL（消除段间网络停顿）
onended: revoke 旧URL → i+1 → play(next)；全部完成→回调收尾
onerror: 重试 1 次 → 仍失败则跳过该段并上报，队列继续
stop():  清队列、pause、revoke 全部 objectURL
```

- 采用**单实例 audio + 预取 Blob** 的乒乓缓冲，实现简单、内存可控；TTS 接口若返回整段音频 URL 则预取退化为 new Image 式预热请求。
- 每段播完立即上报"已播完第 n 句"埋点，便于排查老年患者"听不到声音"类客诉到底是网络段缺失还是播放被拦。
- 后端按句切分 TTS（LLM 分句流式合成）时，前端队列天然承接 SSE 的多段推送。

## 六、结论汇总表：最终推荐技术栈

| 层 | 选型 | 关键版本 | Python 3.9 / 微信内核兼容性说明 |
|---|---|---|---|
| 后端框架 | **FastAPI** | `fastapi>=0.125`（0.125.0 起最低要求恰为 py3.9，主线仍支持） | 最新版可直接用于 3.9.11，无降级惩罚 |
| ASGI 服务 | **Uvicorn** | `uvicorn>=0.30,<0.40`（0.40.0 起弃 3.9） | pip 元数据会自动解析，requirements 仍显式上界 |
| 校验/文档 | Pydantic v2 + 内置 OpenAPI | `pydantic>=2,<3`（2.13.x 仍支持 3.9，下一代将弃） | 关注升级公告 |
| HTTP 客户端 | httpx AsyncClient（长等待+SSE 流式） | `httpx>=0.27` | 3.9 兼容 |
| ORM/迁移 | **SQLAlchemy 2.0 + Alembic** | `sqlalchemy>=2.0` | 3.9 长期兼容；按 §2.4 守则保留迁 PG 通道 |
| 数据库 | **SQLite WAL 模式** | 系统 sqlite ≥3.35（VACUUM INTO 需 3.27+） | 日均 500 会话量级余量充足；busy_timeout=5000 + NORMAL + 短写事务 |
| 前端框架 | **Vue 3 + Vite** | `vue@3.5.x`、`vite@5.4.x`（Node 24 兼容） | `build.target='es2018'` 显式覆盖 Vite 默认 chrome107，兼容 XWeb/旧 X5；Vue 运行时仅需 Proxy |
| 录音采集 | **AudioWorklet → ScriptProcessorNode 降级**，PCM 16k 单声道 WAV base64 | — | XWeb/Chrome66+/Safari14.1+ 走 Worklet；更老内核降级 SPN；零 ffmpeg |
| TTS 播放 | **audio 元素单实例 + Blob 预取队列** + 手势解锁（静音 WAV + AudioContext.resume 同步栈内调用） | — | 规避 iOS 静音键与自动播放拦截 |
| 部署 | Nginx(HTTPS 必须) + systemd + cron `VACUUM INTO` 热备 | — | 生产零 ffmpeg/零数据库服务依赖 |

### 主要风险与缓解

1. **Python 3.9 已于 2025-10 到达 EOL**（安全更新停止）——短期靠依赖 pin + 反向代理收敛暴露面；中期规划升级 Python 3.10+（届时 uvicorn/pydantic 最新版解锁，Django 若要引入也才有可能）。这是环境约束下的已知债务，需写入部署文档。
2. **微信老内核缺 getUserMedia**：上线前真机矩阵实测（R4 专项），保留 JSSDK wx.startRecord 预案。
3. **Vite 默认 target 高于旧内核**：已在工程配置中显式覆盖；CI 可加产物语法检查防回归。
4. **SQLite 写并发上限**：监控 SQLITE_BUSY 计数；触发 §2.4 的量化迁移条件时平滑切 PostgreSQL。
